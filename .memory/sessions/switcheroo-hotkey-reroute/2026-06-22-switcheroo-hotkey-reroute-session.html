## Trigger

The thread started from an incomplete hotkey fix. The user wanted a real default for switch-back, validation for Alt+Tab conflicts, and live automated proof. After that work passed, the user pointed out a deeper behavioral issue: Alt+Tab could move to a recent window, but often failed when toggling back, while switching through the main overlay consistently worked.

## Evidence

- Prior repo-local session HTML at `.memory/sessions/switcheroo-auto-automation/2026-06-18-switcheroo-auto-automation-session.html`
- `Switcheroo/MainWindow.xaml.cs`

## Model

- The main overlay selection path stores `_previousWindow`, sets `_currentWindow`, and uses `AppWindow.SwitchToLastVisibleActivePopup()`.
- The previous-app path was separate. It stored similar state but used `WinApi.ForceSwitchToWindow(...)` directly.
- The user symptom matches that split: the main-window path succeeds, while the previous-app path is less reliable.

## Hypothesis -> verification

- Hypothesis 1: the remaining failures are not from the hook detecting the key, but from the activation primitive used after detection.
  - Verified by code inspection: previous-app used `ForceSwitchToWindow`, while the main overlay path used `SwitchToLastVisibleActivePopup()`.
- Hypothesis 2: if previous-app reuses the main overlay activation path, switch-back reliability should match the successful manual path.
  - Verified by patching `MainWindow` to route both paths through a shared `ActivateAppWindow(...)` helper.
  - Verified by live automation: Notepad + Paint test passed end to end after the reroute.

## Decisions

- Added `Switcheroo/HotkeySelection.cs` to model and validate user-entered hotkeys.
- Made `PreviousAppEnabled` default to `true` with `Alt+Tab`.
- Blocked invalid combinations in `OptionsWindow`:
  - activation shortcut cannot be plain `Alt+Tab`
  - activation and switch-back cannot be identical
  - `Activate Switcheroo with Alt+Tab` cannot coexist with switch-back set to `Alt+Tab`
- Extended automation with `installmainhotkey` and the live `AutomationTests/Test-Hotkeys.ps1` script.
- Rerouted previous-app switching to the same activation path used by the main overlay selection.

## What was not done

- No new unit test was added for the `MainWindow` reroute itself because the behavior depends on live Win32 window activation and is better covered by the real automation harness already present.
- No attempt was made to make modern multi-tab Notepad expose a stable `MainWindowHandle`; the harness instead used Notepad plus Paint, which was more reliable on this machine.

## Open risks

- Synthetic activation-hotkey testing was flaky once before passing on rerun. The live automation should still be treated as timing-sensitive.
- The harness depends on desktop environment details and stock apps available on this host.
