TL;DR

The back/forth app toggle was broken by three stacked causes: the feature was disabled in config, SwitchToThisWindow was denied by the Windows foreground lock, and the switch ran synchronously inside the low-level keyboard hook callback where SetForegroundWindow is also denied. All three were fixed and wired to Ctrl+Shift+Q.

The overlay window list is now ordered: most-recently-used first (tracked by a 500 ms foreground poll), everything else alphabetically by process then title — stable between invocations. Build is clean, 41/41 unit tests pass, the new Debug build is running.

Glossary

Terms
  • WH_KEYBOARD_LL — global low-level keyboard hook; the callback runs on the installing thread's message loop and must return fast.
  • Foreground lock — Windows restriction: SetForegroundWindow is denied unless the caller meets criteria (e.g. received the last input, or lock timeout expired). AttachThreadInput to the foreground thread shares its input state and is the documented workaround.
  • MRU — most recently used; here a HWND list fed by a 500 ms foreground poll and by every switcheroo-initiated switch.
  • Z-order — window stacking order from EnumWindows; top = most recently active. The old list order.
  • Secure desktop — the lock/sign-in screen desktop; LL hooks installed on the default desktop do not fire there.
  • VK 81 / 0x51 — virtual-key code for Q.

## Trigger
- Switcheroo+ (WPF Alt+Tab replacement, repo `G:/github/switcheroo_plus`): the previous-app back/forth toggle hotkey did nothing. User wants it on Ctrl+Shift+Q.
- Window list in the overlay was in "messy" raw Z-order; user wants recent apps on top and a stable order for the rest.
- Follow-up (unfinished at save time): commit changes; Release build via `build.bat` does not open overlay on Alt+Tab; `InternalTrace.*.log` files pollute repo root and should go under a `.log` dir.

## Evidence
- `%USERPROFILE%\.config\.switcheroo_plus\config.jsonc` had `"PreviousAppEnabled": false`, `"PreviousAppHotKey": 69` (Ctrl+Shift+E), `"AltTabHook": false`.
- The previous-app feature already existed in code: `Switcheroo/PreviousAppHook.cs` (WH_KEYBOARD_LL, exact-modifier match via `KeyboardKey.AsyncState`), `MainWindow.previousAppHotkey_Pressed`, config fields, Options UI, and `AutomationTests/Test-PreviousAppHook.ps1`.
- `WinApi.ForceSwitchToWindow` (AttachThreadInput-based) existed but was only used by the automation `setforeground` action; the previous-app path used `SwitchToThisWindow`.
- Automation named pipe `switcheroo_plus_automation` with actions: ping, show, hide, setquery, getwindows, select, activate, previousapp, installprevhook, installmainhotkey, resetprevwindow, getforeground, setforeground, prevstate, setconfig, getconfig, exit.
- `prevstate` after a failed injected Ctrl+Shift+Q showed `prevHwnd`/`currentHwnd` bookkeeping HAD mutated -> hook fired, handler ran, but the actual foreground window never changed.
- Machine locked itself during the final E2E run (foreground = LockApp "Windows default lock screen"); LL hooks do not fire on the secure desktop, so keystroke-level verification of the last fix was deferred to the user.

## Model
- Three hotkey paths: (a) `RegisterHotKey` activation hotkey (Ctrl+Shift+Z, VK 122) -> show overlay; (b) `AltTabHook` LL hook for Alt+Tab interception; (c) `PreviousAppHook` LL hook, generic modifier+VK combo -> toggle to previous window without overlay.
- Toggle flow: `PreviousAppHook.Pressed` -> `previousAppHotkey_Pressed` -> (tracked `_previousWindow` alive and != current ? toggle : walk Z-order with `GW_HWNDNEXT` skipping self and non-`IsAltTabWindow()`) -> `ActivateAppWindow` -> `SwitchToLastVisibleActivePopup` -> `WinApi.SwitchToThisWindow` (old) / `WinApi.ForceSwitchToWindow` (new).
- List flow: `LoadData` -> `WindowFinder.GetWindows()` (EnumWindows Z-order) -> `AppWindowViewModel` list -> sort -> `ObservableCollection` -> ListBox; `WindowFilterer` re-sorts by match score only when a query is typed (stable for empty query).
- Config: JSONC at `%USERPROFILE%\.config\.switcheroo_plus\config.jsonc`, hand-rolled parser/writer in `Switcheroo/Config.cs`; legacy `Properties.Settings` only used for one-time migration.

## Hypothesis -> verification
- H1 "feature disabled in config": CONFIRMED. `PreviousAppEnabled: false` meant the LL hook was never installed.
- H2 "`SwitchToThisWindow` denied by the foreground lock when another app had the most recent input": CONFIRMED. Pipe action `previousapp` (no recent input) toggled both directions; injected Ctrl+Shift+Q did not switch. After switching to `ForceSwitchToWindow`, the first press (Total Commander -> VS) worked.
- H3 "`SetForegroundWindow` is denied while the LL hook callback is still processing the keystroke": CONFIRMED by elimination. Pipe `previousapp` with freshly injected F24 input still worked, so input-recency alone was not the blocker; only the hook-callback context differed. Deferring the switch with `Dispatcher.BeginInvoke` was the fix (verified at pipe level; live keystroke E2E blocked by the machine locking).
- Sorting: verified live via `show` + `getwindows`: after toggling to Total Commander it was index 0 (MRU), all untracked windows alphabetical by process name, foreground window at the bottom.
- devenv elevation ruled out: both devenv and switcheroo_plus run NOT elevated (MainModule accessible).

## Decisions
- config.jsonc: `"PreviousAppEnabled": true`, `"PreviousAppHotKey": 81` (Q). Ctrl/Shift true, Alt/Win/CapsLock false.
- `Core/AppWindow.cs`: added `ForceSwitchToLastVisibleActivePopup()` (ForceSwitchToWindow on the last active visible popup) with a doc comment explaining the foreground-lock denial.
- `Switcheroo/MainWindow.xaml.cs`:
  - `ActivateAppWindow` now calls `ForceSwitchToLastVisibleActivePopup()` and `RecordWindowUsed(target.HWnd)`.
  - `previousAppHotkey_Pressed` reduced to `Dispatcher.BeginInvoke(new Action(TogglePreviousApp))`; new `TogglePreviousApp()` holds the old body; automation `TriggerPreviousApp()` calls `TogglePreviousApp()` synchronously.
  - MRU tracking: fields `_mruWindowHandles` (front = most recent, cap 50), `_foregroundTracker` (DispatcherTimer 500 ms), `_lastTrackedForegroundHwnd`; `SetUpForegroundTracking()` called from ctor; `TrackForegroundWindow()` skips zero/same/self HWND and non-`IsAltTabWindow()`; `RecordWindowUsed()`; `MruRank()` (index or int.MaxValue).
  - `LoadData`: sort `OrderBy(MruRank).ThenBy(ProcessTitle, CurrentCultureIgnoreCase).ThenBy(Title, ...)`; foreground-related window found via `FindIndex(AreWindowsRelated(...))` (was: only if first) and moved to bottom so Enter switches to the previous app.
- `AGENTS.md`: documented list ordering, ForceSwitchToWindow, and the hook-callback deferral rule.
- Built with VS2022 Community MSBuild (`build.bat` equivalent, Debug); NUnit 41/41 passed.
- Old running instance (PID 76164, no automation pipe) killed; new instance started from `Switcheroo/bin/Debug/switcheroo_plus.exe` and left running.
- Edit-tool note: `MainWindow.xaml.cs` has MIXED line endings; `\r` escapes in Edit.old_string did NOT match. Workaround: anchor edits on LF-only lines or use unique single-line strings without newlines.
- NOT done at save time (from Prompt 2): (1) git commit of the 3 modified files (AGENTS.md, Core/AppWindow.cs, Switcheroo/MainWindow.xaml.cs); (2) Release Alt+Tab issue — likely causes identified: config `AltTabHook: false` (handler returns early) and/or Debug instance still running so the Release exe exits on the single-instance mutex; (3) `InternalTrace.*.log` relocation — files exist at repo root (NUnit console internal trace writes them to the CWD); user wants them under a `.log` directory.

## Open risks
- Live Ctrl+Shift+Q keystroke E2E after the `Dispatcher.BeginInvoke` fix is UNVERIFIED (machine locked). If the toggle still fails from the physical keyboard, revisit the hook-callback timing first.
- MRU list is in-memory only: order resets to alphabetical on app restart and re-learns within seconds; stale HWNDs of closed windows linger (cap 50) and HWND reuse could theoretically alias.
- Automation `getforeground` throws on the lock-screen window (invalid handle inside `ProcessTitle`/`ClassName`, `ManagedWinapi.ApiHelper.FailIfZero`) — pre-existing robustness gap, surfaced during testing.
- `TrackForegroundWindow` polls every 500 ms; while locked it may record the lock-screen HWND if it passes `IsAltTabWindow()` (harmless once destroyed).
- Untracked dirs in git status: `.memory/sessions/switcheroo-revert-backup/`, `.temp/` — decide whether to ignore or commit.
- `Switcheroo/HotKey.cs` `LoadPreviousAppSettings`/`SavePreviousAppSettings` are dead-ish (superseded by the LL hook + OptionsWindow single-save path).
